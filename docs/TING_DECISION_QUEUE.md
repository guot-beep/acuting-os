## A. 臨床安全類(建議優先)

### A1 · 方劑安全欄的結構問題(最根本的一條)
**問題**:全庫 **163/224 張卡的 `contraindications_en` 與 `cautions_en` 逐位元組相同**。
兩個欄位不是兩份獨立來源,是同一段英文被翻譯兩次 —— 而「禁用/慎用」的方向詞
是譯者當下決定的。**所以中英方向打架不是翻譯品質問題,是結構必然,修翻譯止不住。**
**選項**:(a) 交給 SOL 重新設計兩欄的語意邊界與填寫規則,再依新規則重灌;
(b) 合併成單一 `safety_notes` 並以方向詞標記每條;(c) 維持現狀,只在眼讀時逐張修。
**不決定的後果**:安全欄的中英矛盾會持續產生,而且每次「修好」的是症狀不是病因。
**決定後**:Fable 出 CONTENT_REQUEST → SOL 供規則 → Sonnet 批次重灌。
來源:`docs/research_packs/FORMULA_EYESON_03.md` F-51。

### A4 · 桂枝茯苓丸的組成整份是別的方的
**問題**:它掛著茯苓丸的組成(逐位元組相同,連英文錯字都跟著搬):列了它沒有的芒硝,
少了桃仁。這是一張標了考試重點的婦科卡。真正的組成只倖存在 `action_profile` 欄位裡。
**選項**:(a) 從 `action_profile` 倖存的正確組成還原(桂枝/赤芍/牡丹皮/茯苓/桃仁 各 9g);

### A5 · 中藥劑量欄有 175 個值是「被存成字串的 JSON」
**問題**:`data/herbs/herb_canon_shortlist.json` 的 `dosage` 欄,187 個字串值裡
**175 個其實是序列化後的 JSON 物件**(`"{\"一般建議\": \"3-9克\", …}"`),
另有 111 個是真的物件。這是**劑量欄位**,而且全庫 grep 找不到任何消費端在讀它 ——
所以目前沒有病人受影響,但它是一顆等著被接上的地雷:哪天有人接上去顯示,
就會把整串 JSON 印給使用者,或更糟,只印出第一個數字。
**選項**:(a) 反序列化成統一物件形狀(機械可做,175 筆);(b) 先確認哪個形狀是正確的
再動(物件 vs 字串兩種來源可能代表不同匯入批次)。
**決定後**:Sonnet 一批可完成,需先驗證兩種形狀的欄位語意是否真的相同。
來源:`docs/research_packs/FIELD_SHAPE_CONSISTENCY_BASELINE.md`。

### B2 · `import_artifacts` 目前有兩種 key 形狀
兩條線同一天各自發明了這個欄位:`{original_field,text,reason,moved_at}` 與
`{field,archived_at,belongs_to,source_url}`。目前兩種都保留、驗證器兩種都接受。
**統一等於改寫既有出處紀錄**,所以留給你決定要不要統一、以哪一種為準。

### B3 · 跨線的「欄位形狀公約」要先落地,才有人能安全正規化
**問題**:全庫掃描找到 **122 個多型欄位**(同一個欄位有時是字串、有時是陣列),
其中 34 個有活的型別專屬消費端 —— 今晚那個「英文模式禁忌區塊靜默消失」就是其中一個。
**但正規化不能各線各自做**:安全欄位(`red_flags` / `cautions` / `contraindications`)
橫跨 8-15 個 collection,若甲線把它統一成陣列、乙線統一成字串,就會再撞一次。
**選項**:在 `data/config/` 放一份形狀公約(例如「安全類欄位一律陣列,單條也用單元素陣列」),
所有線依它正規化;或維持現狀,只在被咬時逐處修。
**已備妥可執行**:掃描報告列出 R1-R4 四批「單一方向、少數側 <30 筆」的安全正規化
(頭皮針 functions/location/needling、藥卡 contraindications 的 1/59 離群、
奇穴 cautionsEn、中藥 indications_en),**等公約確定即可動手**。
`red_flags` 的物件化不在此列 —— 那需要補來源內容,不只是搬形狀。
